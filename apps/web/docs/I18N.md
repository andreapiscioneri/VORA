# Internationalization

Two independent i18n systems — Nuxt's `@nuxtjs/i18n` on web, a hand-rolled React context on mobile — sharing the same 8 languages and the same key namespaces conceptually, but not the same runtime (Nuxt's i18n module doesn't run in React Native, and there's no value in forcing a shared implementation across two different frameworks for this).

## Languages

Italian (`it`, default), English, German, Spanish, French, Russian, Chinese, Japanese.

## Web (`i18n/locales/*.json`)

Configured via `@nuxtjs/i18n` in `nuxt.config.ts`, with `fallbackLocale: 'it'`. **Only `it` and `en` are fully translated.** The other 6 (`de`, `es`, `fr`, `ru`, `zh`, `ja`) are intentionally small scaffolds — enough keys to prove the language switcher and locale plumbing work end-to-end, relying on `fallbackLocale` to fill in the rest from Italian. This is a deliberate, honest scope decision: fully translating every UI string into 8 languages for a project at this stage would be a large, low-value effort compared to the actual product features — the *architecture* (locale files, switcher, `$t()` everywhere, no hardcoded strings) is complete and correct; the *translation coverage* for 6 of 8 languages is not, and is flagged here rather than silently left incomplete.

## Mobile (`mobile/i18n/`)

A custom `I18nProvider`/`useI18n()` context (`mobile/i18n/index.tsx`), **not** `@nuxtjs/i18n` (Nuxt-specific, doesn't run in Expo). Device-locale auto-detection via `expo-localization` on first launch, user-override persisted via `AsyncStorage`, switchable from More → Language with real SVG flag icons (`components/Flag.tsx`) — not text-only.

Unlike web, **all 8 mobile locale files are fully translated** (real translations, not machine filler) — enforced by `mobile/i18n/locales.test.ts`, a Jest test asserting every locale has exactly the same key set as `it.json` and no empty values. This is stricter than web on purpose: the mobile i18n context has no `fallbackLocale` mechanism, so a missing key would either render nothing or throw, rather than falling back gracefully — the test exists specifically to catch that before it ships.

```bash
cd mobile && npm test   # includes i18n/locales.test.ts
```

## Adding a new UI string

**Web**: add the key to `i18n/locales/it.json` and `en.json` at minimum (the other 6 will fall back to Italian automatically); add it everywhere else only if you're doing a real translation pass.

**Mobile**: add the key to **all 8** `mobile/i18n/locales/*.json` files with a real translation in each — the test suite will fail otherwise, by design.

Never hardcode a user-facing string directly in a `.vue` file or `mobile/app/*.tsx` screen — always through `$t()` (web) or `t()` (mobile).

## What's not built

- **Pluralization** — `@nuxtjs/i18n` supports ICU plural rules, but no plural-sensitive string currently uses them (nothing in the UI yet needs "1 task" vs "2 tasks" phrasing beyond simple interpolation).
- **Locale-specific number/currency/date formatting** — dates are currently formatted with plain `Intl.DateTimeFormat`/`toLocaleDateString()` calls where needed, not a centralized locale-aware formatting utility. Currency formatting (relevant to Expenses, CRM opportunity value) is not locale-adapted.
- **Full translation of the 6 non-default web locales** — see above.
